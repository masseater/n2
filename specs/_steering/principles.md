# 開発原則

このドキュメントは、プロジェクト全体で共通して適用される開発原則を定義します。

## TDD（Test-Driven Development）

### 基本サイクル: Red-Green-Refactor

1. **Red（失敗するテストを書く）**
   - 実装前に期待する動作を定義するテストを作成
   - テストが失敗することを確認

2. **Green（テストを通す最小限の実装）**
   - テストを通すための最小限のコードを実装
   - 完璧を求めず、まず動作することを優先

3. **Refactor（コードを改善）**
   - テストが通る状態を維持しながらコードを改善
   - 重複の除去、命名の改善、構造の最適化

### TDD の実践ルール

- **型定義だけを先に作ることは禁止**: 型定義は実装と共に作成
- **テストファースト原則**: 常にテストから始める
- **小さなステップ**: 各サイクルは15分以内を目安

## SOLID 原則

### Single Responsibility Principle（単一責任）
- 各モジュール・関数は単一の責任のみを持つ
- 変更理由は1つだけ

### Open/Closed Principle（開放閉鎖）
- 拡張に対して開いている
- 修正に対して閉じている

### Liskov Substitution Principle（リスコフの置換）
- 派生型は基底型と置換可能

### Interface Segregation Principle（インターフェース分離）
- クライアントが使用しないメソッドへの依存を強制しない
- **警告**: インターフェースを作ることが目的化してはいけない

### Dependency Inversion Principle（依存性逆転）
- 上位モジュールは下位モジュールに依存しない
- **警告**: 実装が1つしかない場合は抽象化は不要（YAGNI）

## YAGNI 原則（You Aren't Gonna Need It）

- 実際に必要になるまで機能を追加しない
- 「将来使うかもしれない」という理由で実装しない
- シンプルさを最優先

### 適用例
- 実装が1つしかないのに抽象層を作らない
- 現在の要件に必要な分だけ実装
- 変更の可能性が低いものはハードコードで十分

## TypeScript 固有の原則

### 型の扱い
- `any` 型の使用は**絶対禁止**
- `interface` より `type` を優先
  - `interface` は既存ライブラリの型拡張時のみ
  - 使用時は必ずコメントで理由を明記
- 型推論を活用し、必要最小限の型注釈

### インポート/エクスポート
- Barrel import/export は禁止
- 各モジュールから直接インポート
- 循環参照を避ける設計
- 型のみのインポートは `import type` を使用

## コード品質基準

### 関数型プログラミングの活用
- 配列操作は `map`, `filter`, `reduce` を優先
- `push` などの破壊的操作は避ける
- イミュータブルなデータ構造を使用

### エラーハンドリング
- 例外は明示的にキャッチし適切に処理
- Fail Fast: 早期に失敗を検出
- ユーザーへの明確なエラーメッセージ

### セキュリティ
- SQLインジェクション対策（Drizzle ORM のパラメータ化クエリ）
- XSS対策（DOMPurify）
- 認証・認可の適切な実装

## コーディングスタイル

### 必須スタイル
- ダブルクォート使用
- セミコロン必須

### 禁止事項
- `any` 型の使用禁止
- 未使用 import はエラー
- 未使用変数はエラー
- barrel import/export 禁止

## アンチパターンと回避方法

### 過度な抽象化
- **問題**: 将来の要件を予測した過剰な設計
- **回避**: YAGNI 原則の適用

### 神オブジェクト
- **問題**: 多くの責任を持つ巨大なクラス/モジュール
- **回避**: 単一責任の原則に従った分割

### コピペプログラミング
- **問題**: 同じコードの重複
- **回避**: DRY（Don't Repeat Yourself）原則の適用

### マジックナンバー
- **問題**: ハードコードされた意味不明な値
- **回避**: 定数として定義し意味を明確化

### 場当たり的な対応
- **問題**: 「一時的」「とりあえず」の修正
- **回避**: 根本的な解決を行う

## 実装時の確認事項

各タスク実装時に以下を確認:

- [ ] TDD サイクルに従っているか
- [ ] SOLID 原則に違反していないか
- [ ] 型安全性が保たれているか
- [ ] `any` 型を使用していないか
- [ ] エラー処理が適切か
- [ ] セキュリティ上の問題はないか
- [ ] テストカバレッジは十分か
- [ ] コーディングスタイルに準拠しているか
